# 本地官方客户端与网页端的功能、加载逻辑对照

检查日期：2026-10-16。对象是本机 `Dev/bilibili` 中的官方 PC 客户端 **1.19.0**，不是对当前所有官方客户端版本的结论。

后续决定：用户明确不需要离线播放库及系统窗口类功能。本轮已完成不改变 UI 的请求与渲染优化，详见 [0.44.5 加载优化](LOADING-OPTIMIZATION.md)；以下保留当时的静态分析与建议。旧客户端及提取的程序代码按用户要求清理，分析文档保留。

读取安装包的 `resources/app.asar`，静态解析主进程、预加载桥、Vue 页面与设置模块；没有运行提取出的代码，没有修改客户端或其登录资料。提取文件保留在本机忽略目录 `dist/bilibili-client-research`，不随维护分支发布。播放器还会从主进程提供的 `playerSrc` 动态加载，网络和解码实现不能仅凭这些静态文件完整判断。

## 客户端的加载逻辑

首页推荐的核心在 `index.7f1a7596.js`，滚动器在 `App.c462a574.js`。以下行号对应本机格式化结果，原打包文件为压缩格式。

1. **分批取数据。** 首页首批 30 项，后续批量按每行卡片数乘 3 计算；会根据容器和卡片高度估算可视行数。不是一次拉完整推荐列表。证据：格式化首页约 9095–9115 行。
2. **滚动触底及请求保护。** 滚动器用 passive scroll，在离底部不足 80px 时触发 `loadMore`；首页请求有 500ms 节流、加载锁、结束标记和失败标记。证据：格式化 App 605–612 行及首页 9104–9119 行。
3. **按 BV 去重。** 合并推荐时排除已存在的普通视频，减少重复卡片。
4. **页面生命周期管理。** 推荐页有约两分钟的重入刷新判断；停用时会裁回首批数据。它能限制部分留存数据，但网页移植时还需要保证滚动位置和返回体验，不能只机械裁剪数组。证据：首页 9186–9192 行。
5. **分块与延后加载。** 路由通过动态 import 加载；主界面准备好后约 800ms 开始串行预热多个页面模块。播放器脚本用一个共享 Promise 避免重复注入。证据：首页 9029、9199–9218 行。
6. **没有在首页推荐中确认通用虚拟列表。** 该滚动器本身只是滚动与触底容器；不能从类名或卡片占位推断已经做了完整虚拟化。

这些是界面和请求调度方式，不能据此证明客户端用了某种专有 CDN 加速。动态播放器、媒体线路和实际吞吐还需要单独网络实测；此前慢网播放优化验收仍按用户决定留到后续。

## Bewly 已有的部分

- `Home/Home.vue` 通过异步组件组织标签页，`KeepAlive` 保留推荐页；外层 `App.vue` 也有页面缓存。
- `App.vue` 已在距离底部 300px 时触发加载，并做了 500ms 节流。这一项没有必要照搬客户端的 80px。
- `VideoCard.vue` 已使用 `content-visibility: auto`；已有封面格式选择和延迟悬停预览。它减少部分绘制工作，但不等于移除离屏 Vue 实例。

## 建议优先级

### 第一优先：推荐请求的生命周期与停止条件

在 `ForYou.vue` 静态发现以下具体风险：

- 网页和 App 推荐请求都在 `finally` 中再次调用自己补页。失败或过滤后不足 30 项时，也可能继续发起新请求；递归调用没有 await，外层加载锁可先释放。
- 补页没有明确的次数预算和连续空页上限。`noMoreContent` 在部分路径被设置后，内部补页没有统一检查。
- 初始化清空数组时，没有重置所有分页和登录/结束状态；刷新索引在请求前递增，失败重试可能跳过批次。
- 模式变化、旧请求返回和页面停用之间，未看到统一的代次标记或取消机制；旧结果可能继续写入当前列表。

建议改为一次加载周期内受控的补页循环：单一进行中的 Promise、有限补页次数、失败停止并显示重试、空页停止、刷新时重置分页、忽略旧代次响应。先验证请求次数和结果一致性，再考虑提升吞吐。本轮没有改动首页请求行为。

### 第二优先：长列表与图片开销

当前推荐卡片仍按完整数组 `v-for`，滚动越久保留的组件越多。建议测量 30、300、1000 项时的 Vue 实例数、DOM、内存和滚动帧时间，再做按行虚拟化，保留搜索、菜单、滚动位置与键盘操作。

封面目前为 eager；可以评估首屏优先、后续图片 lazy、有限预取下一批。悬停预览的请求可做并发限制和失效结果处理。应先测实际请求和缓存命中，避免把已经缓存的能力重复实现。

Vue 官方性能指南也将代码拆分、稳定组件属性和长列表虚拟化作为可选优化方向：[性能优化](https://cn.vuejs.org/guide/best-practices/performance)。这支持上述实现方向，不代表本机已经测得具体加速比例。

### 第三优先：有边界的预热与缓存

可考虑短期保留推荐数据及滚动位置，首次显示后只预热最可能使用的下一页或组件。客户端的全路由预热会增加后台工作量，不应直接作为网页默认策略。性能优化应先保住首屏和可交互时间。
